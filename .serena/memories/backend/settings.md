# Application Settings

- `spatie/laravel-settings` backs application-level settings. Typed classes live in `app/Settings` (`General`, `Authentication`, `Mail`, `UserProvisioning`, `Security`, `Branding`), are registered explicitly in `config/settings.php` (auto-discovery disabled), and persist to the `settings_properties` table.
- Initial values live in settings migrations under `database/settings`; every property must have an initial value so settings always resolve. `SETTINGS_CACHE_ENABLED` (default false) controls package caching; no second cache/repository layer is allowed.
- Never resolve settings directly during bootstrap. Use `App\Settings\SettingsResolver::tryResolve()`, which returns null only for the deployment window (`Schema::hasTable()` returning false, or `MissingSettings` for an unmigrated group); every other failure (connection errors, payload, decryption, casting) is thrown, never silently turned into a default. Its availability memo lives on the container, not in a static, so it cannot outlive the application instance it measured.
- Runtime application happens in `App\Providers\SettingsServiceProvider` (app name, locale, session lifetime, mail sender). Timezone is deliberately not a setting: timestamps travel as UTC ISO 8601 and the frontend formats them in the browser timezone. Password rules come from `PasswordPolicy::rule()` via `Password::defaults()` in `AppServiceProvider`.
- `verified` middleware alias is remapped to `EnsureEmailIsVerifiedWhenRequired` (enforced only when `requireEmailVerification` is on). `EnforceMaintenanceMode` runs in the web group; login/logout/`/up`/`settings.*` stay reachable and `manage settings` holders bypass it.
- Settings has no HTTP surface yet: Form Requests (`app/Http/Requests/Settings`), Actions (`app/Actions/Settings`), and the test-mail Mailable exist, but routes, controllers, and pages arrive together as one vertical slice in the frontend phase. That slice must follow the repo mutation pattern — Inertia `<Form>` → Wayfinder → Form Request → Action → controller → `to_route()` + `Inertia::flash('toast', ...)` — never JSON endpoints or `useHttp`.
- The test mail is sent synchronously to the authenticated manager (`SendTestMail`), never to a submitted address.
- Branding is preset-driven, never a free-form value: `AuthLayoutPreset`, `AppLayoutPreset`, `ColorThemePreset`, `FontPreset` (there is no `primaryColor`). `App\Http\Presenters\BrandingPresenter::present()` builds the explicit scalar array shared as the `branding` Inertia prop - the settings object itself never crosses the boundary - and `::defaults()` backs both the pre-migration fallback and the root Blade view. `resources/views/app.blade.php` renders `data-color-theme` / `data-font-preset` on `<html>` server-side to prevent FOUC; `resources/js/lib/branding.ts` + `composables/useBranding.ts` mirror them onto `document.documentElement` and map presets to layouts through explicit component maps (never a constructed import path). `.dark` still owns light/dark; a color preset only swaps brand tokens, and every preset ships a light and a dark block in `resources/css/app.css`. `branding.companyName` is the single source of visible identity - logo, auth split header, the server-rendered `<title>`, and the client `brandedTitle()` callback all read it, never `props.name` or `VITE_APP_NAME` (which survives only as a fallback). `branding.footerText` renders through `AppFooter.vue` in every auth and app layout. `npm run test:branding` guards those invariants.
- `UserProvisioningSettings::$defaultPassword` is encrypted (`encrypted()`), write-only, and excluded from `toArray()`/`toJson()`, which expose `hasDefaultPassword` instead. It lives in its own group precisely so no other runtime concern (session lifetime, policy, queue refresh) decrypts the secret just to read a neighbouring property. It is never seeded, hardcoded, logged, or flashed. `UpdateDefaultPassword` / `ForgetDefaultPassword` are separate actions: an empty form input keeps the stored password, clearing is explicit.
- `CreateUser` takes only name and email. It returns an existing user by email *before* requiring the default password, so a retry stays idempotent after the setting is cleared. For a new user it throws `App\Exceptions\DefaultUserPasswordNotConfigured` (message translated from `setting.user_provisioning.default_password.not_configured`) when unset, assigns the plaintext so the model's `hashed` cast produces a per-user hash, and sets `must_change_password = true`.
- Changing `passwordPolicy` is rejected (validation error on `passwordPolicy`) when the stored default password would not satisfy the target preset; the policy is never weakened to accommodate it.
- `SettingsServiceProvider` re-applies settings on `Queue::looping` so long-running workers do not keep booted-at-start values.
- Feature tests fake `UncompromisedVerifier` globally and default to the basic preset via `usePasswordPolicy()` in `tests/Pest.php`; password and authentication tests opt back into the real preset with the same helper. `settingsManager()` creates a user holding `manage settings`.
